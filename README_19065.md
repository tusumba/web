# #19065 — Веб: очередь заявок и решение модератора

Исходная база: `tusumba/web`, ветка `feature/19064-web-auth` (PR #19064 должен быть согласован и принят до #19065).

## Реализовано

- В личном кабинете для роли moderator появляется ссылка на очередь.
- `/moderation/applications`: очередь заявок с фильтрами по статусу и типу, постранично по 20, состояния loading / empty / error, повтор запроса.
- `/moderation/applications/:id`: карточка мероприятия или секции с фактическими полями OpenAPI и автором (UUID).
- `approve` подтверждается в диалоге; `reject` требует непустого комментария до 1000 символов.
- При `409 application_already_processed` карточка заново загружается, решение не повторяется.
- Ролевой UI-guard по `roles` access JWT: `moderator`. Это **не проверка безопасности**; сервер обязан отвечать 403 остальным ролям.
- HTTP-клиент Moderation (`openapi-fetch`) работает с `SessionManager.authenticatedFetch` из #19064; не создаёт собственную очередь refresh.
- OpenAPI срез `openapi/moderation.yaml` по исходному `tusumba/moderation-service/docs/openapi.yaml` (`main`, проверен на момент подготовки). Источник истины — репозиторий бэкенда.
- Unit-тесты валидации решения и извлечения ролей JWT; визуальный стиль Tusumba Material 3.

## Проверка

```bash
npm install
npm run generate:api
npm run lint
npm run test
npm run build
```

Чтобы проверить на стенде: войти в аккаунт с ролью moderator, открыть `/moderation/applications`, просмотреть заявку on_review, одобрить её. Затем дождаться события `ApplicationApproved` и появления объекта в каталоге Events (асинхронное действие). Проверить отдельно `reject` с комментарием, `403` для user, `409` при двойном решении и повторную загрузку после ошибки сети.

Важно: без развернутых Identity, Moderation, Events, RabbitMQ и gateway нельзя подтвердить сквозную приёмку. В интерфейсе после 200 approve написано «публикация выполняется», а не «событие уже опубликовано».
